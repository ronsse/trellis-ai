### 7.3 K2 — the graph reports its own shape

Branch `feat/graph-shape-sensor` @ `906d4db`, cut from `origin/main` @ `1ef5c9c`.
`trellis analyze graph-shape [--format json]`, read-only, one read pass, in a new
module (`src/trellis/analyze/graph_shape.py`).

**The API has no cursor**, so "no cap" is sized rather than paged: the limit is
`count_nodes()` / `count_edges()` plus a margin, and a read that comes back *at* its
limit raced a writer, so `status="truncated"` and a note names which query. A partial
prefix is never served as a census. Degree comes from the edge list in memory, so
`get_edges` is never called — the tests proxy the store and fail if it is.

**Prod gate.** Read-only, `REPEATABLE READ`, one snapshot, with the sensor's output
cross-checked against the same quantities re-derived independently in SQL *inside that
same transaction*. All five agree exactly: nodes, edges, isolated, document-linked,
max documents per node.

The `PostgresGraphStore` was deliberately **not** constructed. Its `__init__` runs
`CREATE TABLE IF NOT EXISTS` plus the `ALTER TABLE` migration list, and this branch is
newer than the deployed build (`2e62ffe`), so instantiating it could have migrated
prod's schema. Its row mappers are classmethods and were reused without instantiating
anything. Probe: `$SP/k2-prod-probe.py`; full report `$SP/k2-prod-report.json`.

**#594's figures, re-derived four days later.** Every rate is stable; counts drift with
ingest.

| | #594 (09-16) | 09-20 |
|---|---|---|
| current nodes | 1896 | 1936 |
| current edges | 1945 | 1988 |
| isolated | 213 (11.2%) | 223 (11.5%) |
| isolated in `gotcha`/`concept`/`system` | 163 | 171 |
| `gotcha` isolated / total | 72 / 72 | 80 / 81 |
| any `document_ids` | 180 (9.5%) | 191 (9.9%) |
| max `document_ids` per node | 1 | 1 |

`gotcha` is **80 of 81**, not 72 of 72. One has acquired an edge. That is the whole
argument for having the sensor: "all of them" was a point-in-time fact being carried
forward as a structural invariant.

**#594's false collision claim is now a reported quantity rather than a correction.**
The issue said three of seven cross-type name collisions were casing collisions on the
type itself; zero were. The report carries the number the claim was reaching for:
raw-type collisions 6, canonical-bucket collisions 6, `explained_by_alias_map` **0**.
The alias map explains none of them. And `top_hubs` carries each hub's *type*, so the

### 7.5 · K4 — referent identity (PR #599, `docs/design/adr-referent-identity.md`, status Proposed)

**The premise needed correcting before the decision could be made.** The corpus inherited
#594 §6's framing — the same file mentioned twice is "two string spellings that happen to
match, or happen not to." Measured, that is largely false. Across the 133 path-like node
names there are **zero collisions by exact name string**, and this is not luck: for the
`artifact:` namespace the minted id *is* the verbatim name, so two producers who type the
same string converge by construction. Real divergence is 4 suffix pairs, 5 basename groups,
14 redundant ids across all 1,945 distinct current names.

What is actually broken is that **the key which converges is under-qualified**. 991 nodes
denote something living in another system (SoftwareApplication 851, File 125, Dataset 7,
Device 4, API/Command/SystemdUnit/Wrapper 1 each) and **zero carry any locator property at
all**. 30 node names are absolute paths and **none** carries a machine or host; 4 of 133

happened — seven separate `hermes` nodes against an empty alias table.

**Panel: unanimous on B** (bind an `EntityAlias` per `(source_system, raw_id)`), 0.72 and
0.85, non-overlapping reasoning, exit 0. Both panelists' `top_risk` items were verified
against the code and **both survived**, which is the outcome the skill's verify step exists
to produce and the reason the ADR has a §3 and a §5.

**Two findings the panel could not have had, both from the mandatory verify pass.**

*First, `adr-alias-resolution.md` (Accepted 2026-05-05) is a prior attempt the brief did not
include.* It had already fixed `(source_system, raw_id)` as the natural key, already named
this exact footgun verbatim — "silently unreachable through the alias path — no error, no

three collision guards, rejecting (a), deferring (b) `allow_repoint` and naming (c)

mechanism being chosen. **Grepping the design directory for the primitive's own name is
cheaper than the panel run that follows it.**

Note the shape of (a)'s rejection, because it is why this ADR may namespace anyway: the
stated cost was "UX regression for `retrieve entity user-api`", which is specific to
`LOCAL_SOURCE_SYSTEM` and bare-label CLI lookup. Outward referents are resolved by
producers, not by humans recalling a label. **A rejection is scoped to the surface that

*Second, the panel asserted a property that is backend-dependent.* "Scopes collisions to

on `version_id` alone; one-current-per-pair rests on `upsert_alias`'s close-then-insert.
`entity_resolution.py`'s header says this explicitly and warns against reading its own
prose as the stronger claim. A unanimous panel stated the stronger claim anyway.

**The decision is B and B alone is insufficient, and the ADR leads with that.** Uniqueness is
scoped to `(source_system, raw_id)`, so a qualifier only disambiguates from inside one of
those two fields — and producers capture none (0/991). Binding aliases from what producers
emit today would bind under-qualified `raw_id`s and reproduce the collapse one layer down,
now with a serialization point making it durable. **Qualifier capture is a prerequisite, not
a follow-up; adopting §2 without it is worse than the status quo**, because it converts an
ambiguous name into an authoritative binding. That sentence is the deliverable, more than
the letter B is.

Also recorded: ontology §5.3 is titled "Aliases are documented as deprecated, not removed"
and is about legacy **type-name enum values**, not `EntityAlias` rows — §5.1 preserves that
table by name. A future reader skimming headings would get this backwards, so the ADR says
it out loud.

never been written to by any production code path" is true of the *deployed* build only —
#530 on `main` populates it under `source_system="name"` via `bind_alias_if_absent`. And
this is forward-looking work, not a live repair: 127 of 133 path-like nodes carry

referents today, which is exactly why exact-string convergence has sufficed so far.

### 7.6 K3 — not built. The ceiling is 7 nodes, and the instruments cannot see the case that matters

**Skipped under §3's own escape clause** ("Otherwise record the ceiling in §7 and
skip"). Nothing was written to `src/`. The measurement below is the deliverable.

**K2's gate reading was too generous, and the correction matters.** §7.3 says the gate
is met because `Tool` (3 nodes) is an uncovered split "beyond `System`". But `Tool` is
not a *second* split — it is the third raw spelling inside the *same* group as `System`,
and at 3 nodes it is **smaller than the 4-node `System` case §3 named as the benchmark
for too-small**. The group's headline "36 nodes, 1.9%" also over-states the uncovered
half by a factor of five: 29 of those 36 are raw `system`, which the alias map already
covers. The uncovered population is `System` (4) + `Tool` (3) = **7 nodes, 0.362%**.

**The ceiling, run through the actuator's own generator.** K3's proposal rule was to be
the shipped `_type_warnings._closest_match`, so the ceiling is not an estimate — the
predicate was executed over every raw type and edge kind in the prod census (1,936
nodes / 1,988 edges, snapshot of §7.3):

| | nodes | share |
|---|---|---|
| already known (canonical, alias, or legacy enum) | 1,818 | 93.9% |
| **K3 would propose an alias for** | **7** | **0.362%** |
| no suggestion | 111 | 5.7% |

Edge kinds: **all 1,988 edges carry a known kind. Zero proposable.** The two proposals
are `System → system` and `Tool → tool` — both pure case variants of alias keys already
in the map (`system` and `tool` are entries; the capitalised forms are not, because
`canonicalize_entity_type` is an exact-match dict lookup). An actuator with a mining
pass, a report surface, a paste-ready fragment and a human Tier-3 gate, to emit two
dictionary entries that differ from existing entries by one letter's case, is not worth
building. Its whole output can be written by hand in the time the report takes to read.

**And there is no retrieval impact to buy.** Both live callers were checked:
`retrieve/strategies.py:1486` only *stamps* the canonical type as `PackItem` metadata,
and `retrieve/observation_strategy.py:201` gates on it but only against
`{Observation, Measurement}`, which neither `System` nor `Tool` is. So the 7 nodes are
mis-bucketed in analytics and mis-stamped in pack metadata; **no memory is hidden from
any query**. This is not the #282 hard-exclusion shape.

**The finding worth more than the actuator: both instruments are blind to the one case a
human would call drift.** `Software` (3 nodes) is a near-miss of `SoftwareApplication`
(843 nodes) and *neither* instrument can see it, for two independent structural reasons:

- `_collect_uncovered_splits` groups by `canonicalize_entity_type(raw.lower())`. For
  `Software` that is `'software'`; for `SoftwareApplication` it is
  `'softwareapplication'`. Different groups, each of size one, so no split — **by
  construction the detector can only find raw types that already agree after
  canonicalization**, i.e. spellings the alias map *nearly* covers. A spelling it does
  not cover at all is invisible.
- `_closest_match` skips any candidate whose length differs by more than 1 from both the
  raw and normalised value. `Software` is 8 chars, `SoftwareApplication` is 19, so the
  candidate is skipped before the distance is computed (it would be 11 anyway).

So the instruments answer "which spellings does the alias map nearly cover?" and the
question that was being asked is "which spellings are drift?". Those are different
questions, and on this corpus they have almost disjoint answers.

**The other 111 are not drift and must not be proposed for.** 88 are `save_knowledge`
memory types (`gotcha` 81, `decision` 3, `lesson` 2, `constraint` 1, `procedure` 1),
~12 are analytics artifact types (`*Report`, `NoiseTagsApplied`), and 11 are free-form
extractor mints (`Device` 4, `Software` 3, `API`/`Command`/`SystemdUnit`/`Wrapper` 1
each). The open-string contract exists for exactly these. `_closest_match` correctly
returns `None` for all of them — a true negative, not a miss.

**Why the two entries were not just written.** Adding them is a two-line edit and ADR
line 310 says "adding a new alias is cheap" — but every one of the map's 10 keys is
lowercase, and `adr-graph-ontology.md:212` describes it as "(legacy lowercase →
PascalCase / camelCase)". `System` and `Tool` are PascalCase mints by the live trace
extractor, not legacy data, so they would be the first keys to violate the map's stated
domain. The alternative one-line fix — lowercase the key before the alias lookup — is
strictly more general but silently widens the rewrite surface to *any* future PascalCase
type whose lowercase collides with an alias key (`Service`, `Document`), which the
open-string posture argues against for a 0.362% benefit. **Which of those is right is an
ontology call under a "one-way commitment", not a mechanical one**, so it goes to §5 as
a question with both options and the number attached, rather than being decided here.

**Owner queue addition.** Should `System` and `Tool` (7 nodes) become alias entries,
become canonical types in their own right, or be left as open strings? Same question for
`Software` (3 nodes) against `SoftwareApplication`. Leaving them is a defensible answer —
the cost today is an analytics bucket, not a lost memory.

### 7.7 M1 — the warnings nobody carried (PR #600, `fix/m1-dropped-warnings`)

The item read: *"The `executor.execute` call sites that drop `CommandResult.warnings`
(25 when C2 counted them): re-count, then surface them or derive a rule."* The re-count
on `1ef5c9c` is **35 sites, 34 dropping**, with the sole reader being MCP
`execute_mutation` at `src/trellis/mcp/server.py:3105`. So the answer was *both*: surface
them where a caller exists, and derive a rule where the surfacing could silently rot.

**What C2's framing got slightly wrong, and it matters.** The item is phrased as a
call-site problem — as though 34 callers were each failing to read a field that was
sitting there for them. Two of the three defects are upstream of any call site. The
executor itself dropped the warnings on **every outcome except success**, so on the
REJECTED path there was nothing at the call site to read; and `CommandResponse` had no
`warnings` field at all, so the three REST routes could not have forwarded them if they
had tried. Counting call sites finds the symptom. Only reading the producer finds that
the gate accumulates warnings *before* it reaches the rule that blocks — which is
exactly the case (a `warn` rule firing ahead of a `deny`) where a caller most needs to
be told.

**Provenance.** `warnings=policy_warnings` reached `CommandResult` in `1e6c66e` (C1,
[#370](https://github.com/ronsse/trellis-ai/issues/370)); the MCP reader arrived in
`5c0e784`. So #370 made warnings reachable and nobody checked whether anything reached
for them. **All three defects are latent today** — the [#461](https://github.com/ronsse/trellis-ai/issues/461)
shape — because the gate is the only producer and Trellis ships zero policies. They go
live with the first declared policy, which is also when nobody will be looking.

**The fix is a uniform invariant, not a patch to the paths that looked important.**
Every outcome reachable after Stage 2 now carries the warnings, on the `CommandResult`
*and* on the emitted event; Stage 1 is the one exception, because it runs before the
gate. Forwarding them only where it seemed to matter is how this was lost the first
time, and a special case is a roster the next reader has to re-derive.

**The conditional/unconditional split is deliberate and the two halves disagree on
purpose.** The DTO and CLI-JSON keys default to `[]` and are *always* present, so
"the gate ran and nothing warned" is distinguishable from "this build predates the
field" — [#404](https://github.com/ronsse/trellis-ai/issues/404)'s precedent. The audit
*event* keeps its conditional `policy_warnings` key, because
`TestDefaultPostureIsTransparent` pins a zero-policy deployment to a byte-identical
payload. The CLI *text* path prints nothing when empty: a human surface has no parser
to mislead.

**The rule pins two properties, and the second is the load-bearing one.** Three routes
had each hand-written the same five-field copy of `CommandResult` — the
[#456](https://github.com/ronsse/trellis-ai/issues/456) smell — so they collapse to one
`command_response()` in `src/trellis_api/routes/_results.py`. But a site count alone
stays green through a *single* projection that quietly stops setting `warnings`, which
is this same defect with a smaller blast radius. So
`tests/unit/api/test_command_response_rule.py` asserts the class is built in exactly
one file **and** that the construction passes every field the DTO declares, with a
behavioural round-trip underneath: widening the structural exemption list to wave
`warnings` through does not silence it.

**Seven mutants, three source-side and four rule-side, each killed by the guard written
for it** — and the executor tests re-run against the pre-fix source fail **9**, one per
newly forwarded outcome, while `TestDefaultPostureIsTransparent` passes on *both*
versions, correctly, because it asserts a property both have.

**Residue, counted rather than silently skipped.** `IngestResponse` (2 sites),
`BulkItemResult` (3), the five non-`execute_mutation` MCP capture tools (return shapes
are heterogeneous — `str`, markdown, a tuple, `json.dumps` — so no one helper covers
them and adding a field to each is an API-design call), CLI ingest / demo /
extract-refresh (5), the six internal hooks (no caller to tell; the event payload is
their record), and the `no_handler` branch, which emits no event at all.

**D3 routed, not fixed.** `Enforcement.AUDIT_ONLY`'s only observable is
`logger.info("policy_audit")`, which the CLI's `WARNING` default discards — so the
audit level is invisible on the surface most likely to be running it. A durable record
means widening the `PolicyGate` protocol's return tuple; raising the log level
contradicts the level's documented "silent to the caller" contract. Both are real
changes with real blast radius, so this is §5, not a quiet TODO.

Gate green: ruff clean, `mypy` 341 files, **7744 passed / 27 skipped / 366 deselected**.
`docs/api/v1.yaml` regenerated **inside the commit**, because `make openapi-check` is
`git diff --exit-code` and an uncommitted regeneration makes every mutant report as

**No `Issue:` trailer** — M1 has no tracker issue. Verified, not assumed:

### 7.8 M2 — a contract suite runs only insofar as an executed module inherits it (`6331b6d` onto #583)

Two PRs built `tests/unit/test_ci_coverage_rule.py` independently, a day apart. #578's
is contract-scoped: it models `TargetSite` / `PytestLeg` / `ContractFile` and asks one
question of `tests/unit/stores/contracts/`. #583's models the whole tests tree — 391
files, ~7,000 nodes — and wires the 99 tests that ran nowhere. #583 is the survivor, so
M2's job was to make sure closing #578 does not take its one irreplaceable relation with
it.

**Why that relation cannot be asked by the rule that supersedes it.** #583 reasons over
files pytest collects, `test_*.py`. A shared contract suite is not one:
`graph_store_contract.py` defines the spec and collects nothing, running exactly insofar
as some *executed* module subclasses it. So the suite is not in the population at all,
and **absent from the population renders identically to covered**. `GraphStoreContractTests`
could pin 106 semantics no backend has ever been measured against and the coverage rule
stays green. That is #579 read from the other side.

**The measurements came before the code, and two of them changed it.**

- The structural definition of a suite — *any uncollected class holding `test*` methods* —
  finds **exactly six** tree-wide, all in `contracts/`, with no false positives: Blob 22
  methods, Document 57, EventLog 31, Graph 106, Trace 27, Vector 38.
- All **14** subclasses are direct, `Test*`-prefixed, and inside `contracts/`. Zero
  outside. So #578's narrow scan and a tree-wide scan **return the same answer today** —
  which is exactly why the difference had to be proved somewhere other than the live tree.
- `_uncovered_files()` live: 3 uncovered of 391, and all 14 contract modules covered. The
  rule is green on arrival, like K5's two rosters.
- Of the 6 workflow legs, `publish.yml` job=test is the only `pr=False` one and
  contributes only unmarked coverage `tests.yml` already gives — so using #583's all-legs
  `_file_is_covered` instead of #578's PR-legs-only join costs nothing today and keeps
  one definition of "runs" in the file.

**Four deviations from the ported original, each with its reason.** Population structural
rather than directory-scoped; subclass scan tree-wide rather than `contracts/`-only;
executed defined by #583's own join; and the covered set taken as the **complement** of
`_uncovered_files` over the same walk rather than computed a second time — #464, where two
counters over one tree drift silently and in the worst direction.

**Separate exemption map, and the reason is not tidiness.** `DELIBERATELY_UNSUBCLASSED`
cannot share `DELIBERATELY_UNWIRED`: that map's key space is files pytest collects, and
its stale-direction check asserts its entries are *uncovered*. A suite module named there
would be reported stale by the very rule protecting it. Both maps are empty, and the
comment says why that is a claim rather than a placeholder — all six suites have a
PR-covered subclass, true only since #543 gave the ArcadeDB graph contract a service
container. **#579's gap is invisible to this rule by construction**: an absent subclass is
not something a rule about subclasses that exist can see. Hence an issue, and #589 open
against it.

**Five floors, not four** — `SHARED_SUITE_FLOOR = 5` against six. The two halves of the
relation fail in opposite directions and only one is loud: an empty base set reports all
six suites unreached and is impossible to miss, while an empty **suite** set passes over
nothing at all. The floor guards the silent half. It sits one below the true count
because consolidating two suites is ordinary and deleting a store ABC arrives with its own
review.

**Mutants: five, all dead, and the interesting one is invisible to production.**

| mutant | dies on |
|---|---|
| suite population drops the test-method guard | the live rule |
| subclass scan restricted to `contracts/` | **the synthetic corpus only** |
| executed bases read every test file, not the covered ones | synthetic corpus |
| seed from every class, not only `Test*` | synthetic corpus |
| direct bases only, no transitive closure | synthetic corpus |

live tree **cannot** separate the narrow scan from the correct one, because every subclass

### 7.10 M4 — the actuator order was the wrong axis (`43439f8`, `plans/capability-self-improvement`)

nothing to merge. So the fix is not to permute the table but to say it is not a queue, and
to derive the build order from the rule §5.2 already states: **measure the ceiling before

degree 2.05 both times, isolation 11.2% → 11.5% — which is what licenses building on these
base rates at all.

have no edges (182 of 196 isolated, 93%), and the nodes that *are* external referents have
no addresses. Edge-minting and qualifier capture are not two independent prerequisites
